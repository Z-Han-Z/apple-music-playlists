# 把歌词与乐评接进评价体系

这份文档回答一个具体问题：**歌词和乐评能不能进评价体系，怎么进，代价是什么。**
每条"已实测"都是在本机跑出来的；没验证的会明确标出来，不混在一起。

---

## 0. 结论摘要

| | 可得性 | 覆盖（本机实测） | 主要价值 |
|---|---|---|---|
| **歌词** | ✅ Apple `amp-api` 可用；第三方源作补充 | **65.1%**（1029/1581） | 主题契合**从猜测变成有据**；**排除纯音乐/伴奏** |
| **乐评** | ✅ Apple 编辑评语免费；外部源部分可得 | 未测 | 质量先验 + 给 agent 讲语境 |
| **人声/器乐判定** | ✅ **已实现**（`playlist_core.classify_vocality`） | 见 §2.4 | 直接可用，不需要联网 |

### 分工（已定）

```
服务端（MCP）      采集 + 聚合信号 → 结构化交给 agent，**自己不评分**
宿主 agent 的 LLM  综合歌词 / 乐评 / 音频特征 / 元数据 → 做评价
```

**服务端的职责是"喂料"，不是"算分"。** 这符合项目既定的"服务端不内嵌 LLM"，
也让评价能力跟着宿主模型一起升级——服务端不用维护词表、权重或评分逻辑。

**因此不做本地情感词表。** 上一版把词表打分当作"唯一干净的解法"，那是为了绕开
"歌词不能外传"这个前提。既然歌词文本可以交给 LLM，整条路就不必要了：
不用引入词表数据依赖、不用赌中日文情感分析的质量、不用维护第二套评分。

### 让 LLM 的判断驱动数值优化器

排序 cost 是**数值的**（退火要数字），评价却由 LLM 做——两者怎么接？

> **让 LLM 产出数字，让服务端消费数字。**

服务端不评分，但可以**接收调用方给的每首分数**（例如 LLM 读完歌词后给的
`lyric_valence` / `theme_fit`），当作弧线的额外一轴。这样"服务端不内嵌 LLM"和
"LLM 综合判断"同时成立，而且 LLM 的结论真的**能进排序**。
这是把 §2.4 那些信号接进优化器的唯一入口。

### 唯一的负向结论（保留）

**乐评进不了排序 cost。** 专辑级、静态、不描述"这两首接在一起好不好"。
硬塞进去会让 cost 失去可解释性——而可解释性是这套 cost 唯一的凭据。见 §1。

---

## 1. 现在其实是两套评价体系

| | **排序 cost**（相邻 / 位置相关） | **选曲得分**（单曲/专辑，静态） |
|---|---|---|
| 现状 | 4 条相邻规则 + 弧线偏差（valence/energy/loud/tempo） | **没有**——主题契合全靠 LLM 凭标题/艺人/流派推断 |
| **歌词**能提供 | **歌词情感弧**（独立于音频 valence）；跨曲呼应检测 | 主题契合度（可验证）；语言分布；**反讽量** |
| **乐评**能提供 | ❌ **几乎不能** | ✅ 质量先验；语境；`contentRating` 过滤 |

乐评是**专辑级、静态、不描述"这两首接在一起好不好"**。它属于"选哪些歌进来"，不属于"这些歌怎么排"。
把专辑评分混进相邻惩罚，会让 cost 失去可解释性——而可解释性正是这套 cost 唯一的凭据。

## 2. 歌词

### 2.1 获取方式（已实测）

| 主机 | `/v1/catalog/{sf}/songs/{id}/lyrics` |
|---|---|
| **`amp-api.music.apple.com`** | **HTTP 200** |
| `api.music.apple.com`（官方文档主机） | HTTP 400 `Insufficient Permissions` |

**和 `DELETE`、`include=audio-analysis` 完全同一个规律：必须走 amp-api。**
用现有的 developer token + music-user-token 就行，不需要额外凭据。

**载荷**：`data[0].attributes.ttml` —— TTML XML。实测一首的结构：

```
标签计数: {tt, head, metadata, iTunesMetadata, translations, songwriters,
          songwriter×2, body, div×9, p×65}
有 begin=/end= : True      ← 关键
有 ttm:agent   : False
```

两个结构性事实：

- **歌词是按行对齐到时间的**（`begin` / `end`）。不只是纯文本——可以把某一行定位到歌曲的某一秒。
  这对"某首歌在前 30 秒就点题"这类判断有用。
- **不分歌手**（无 `ttm:agent`），合唱无法区分声部。

**零成本预筛**：`hasLyrics` 就在**现有的 catalog 响应里**——`am_meta.catalog_meta()` 已经在拿这个字段了。
`hasLyrics: false` 的曲子请求歌词返回 **404 `No related resources`**（不是权限错误，是真的没有）。

### 2.2 覆盖率（本机实测，音乐库 1581 首）

```
有歌词：1029/1581 = 65.1%
```

按流派（曲目数 ≥30）：

| 流派 | 覆盖 | |
|---|---|---|
| 音乐剧 | 100% \| 47 首 | |
| 另类音乐 | 94% \| 82 首 | |
| J-Pop | 91% \| 205 首 | |
| 动画 | 88% \| 412 首 | ↓ 你这个库的主力 |
| 摇滚 | 79% \| 228 首 | |
| 国际流行 | 70% \| 30 首 | |
| **电子音乐** | **32% \| 50 首** | |
| **原声音乐** | **11% \| 129 首** | |
| **爵士乐** | **11% \| 56 首** | |

**65% 这个数字低估了可用性。** 缺口集中在**器乐**（原声、爵士、电子）——而那些曲子本来就不需要歌词信号。
对"歌词真的有意义"的曲子，有效覆盖约 **80–90%**。

**一条干净的因果链**：`(无流派) 0/186` 的 186 首，与之前测出的**没有 ISRC 的 186 首是同一批**。
没有 ISRC ⟹ catalog 拿不到属性 ⟹ **既没有流派，也没有歌词**。于是：

```
186 首（11.8%）  对任何 catalog 信号都不可达
1395 首中 1029 首有歌词 = 73.8%
```

### 2.3 版权与分工（已定）

**歌词文本可以交给 LLM。** 这是使用者的判断，它解开了上一版文档里的死结——
那一版把"歌词不能外传"当作硬约束，于是和"服务端不内嵌 LLM"无法同时满足，
只好提出本地情感词表作为唯一出路。前提改了，那条出路就不需要了。

于是：

- **不做本地情感词表**，不引入词表数据依赖
- 歌词文本随其他信号一起交给宿主 agent 的 LLM 综合判断
- 服务端只负责**取到、清洗、结构化**（见 §0 的分工与"LLM 产出数字"那一节）

**仍然成立的一条：歌词不要进仓库、不要进测试夹具。**
它是授权内容——放在 `docs/` 或 `tests/` 里就不是"自己机器上看看"了。
缓存写用户目录（已 gitignore）没有问题。

**③ 覆盖率仍然是天花板。** 和 ISRC 一样：没有歌词就没有歌词信号。
而且这个天花板**可以靠第三方源抬高**（见 §2.5）——实测有 217 首是"有元数据但 Apple 没歌词"，
正是第三方源的目标。

### 2.4 怎么进评价体系

**(0) 排除纯音乐、伴奏 —— ✅ 已实现**

`playlist_core.classify_vocality()` 按**确定性从高到低**判定：标题标记 → 歌词证据 → 时长。
规则与词表都在 `playlist_core`（平台无关、可离线测试，195 项测试里有一条盯着它），
`playlist_audit` 的第【8】节已经在用。

实测你的库 1581 首：

| 判定 | 保守（不把 Apple 的 hasLyrics 当歌词证据） | 把 Apple 的 hasLyrics 当歌词源 |
|---|---|---|
| 标题写着器乐/伴奏 | 12 | 12 |
| 多半是器乐（查过的源都没收录） | — | **403** |
| 过场/间奏（<2:00） | **158** | 137 |
| 未知 | 1411 | 0 |

三个值得注意的地方：

- **标题标记只抓到 12 首（0.8%）**——光靠标题远远不够，"标题里写着伴奏"这个启发式
  比直觉上弱得多。它可靠，但它覆盖不到什么。
- **<2 分钟的曲子有 158 首（10%）**——本库里游戏原声占比很高，而这类发行常有大量短 cue。
- 403 那批可以再分解：**186 首根本没有 ISRC**（拿不到任何属性）+ **217 首有元数据但 Apple 没歌词**。
  **那 217 首正是「找第三方歌词源」的目标**——这不是猜的，是两个实测数字相减。

**(a) 排序 cost：歌词情感弧（最有机会）**
现在弧线只吃音频 `valence`（来自 Reccobeats）。歌词情感是**独立信号**。两者分开看，并新增一个**反讽量**：

```
irony = |audio_valence − lyric_valence|
```

音频欢快、歌词惨烈——它在排序上是一个**有意的位置**，而且天然属于"有意思"那一层。

**(b) 选曲得分：主题契合（最实用）**
自然语言流程里最难的一步是"这首歌到底贴不贴主题"。现在 LLM 只能从标题/艺人/流派推断。
歌词让这一步**可验证**，而不是靠感觉。

**(c) 跨曲呼应检测（最"有意思"）**
实测那张六幕一日歌单里就有一例**跨曲意象呼应**（两首歌的标题共享同一个意象，构成首尾闭环）——
**当时是我人工发现的**。用共享的稀有词可以自动检出候选对，然后把它们安排在弧线的两极。
这一步纯离线，不需要新数据源，只需要歌词特征。

**(d) 覆盖率漏斗新增一层 `no-lyrics`**
`playlist_core.COVERAGE_STAGES` 加一层。这样"这张歌单有多少能被评价"仍然**只有一个答案**，
而不是又多出一套说法——这是那张表存在的全部意义。

### 2.5 外部歌词源

| 源 | 说明 | 状态 |
|---|---|---|
| **LRCLIB** | 免费、无需 key；按 artist/title/album/duration 匹配，返回同步或纯文本歌词。Apple 缺歌词时的自然回退。甚至有现成的 `mcp-lrclib` | 搜索确认存在（[lrclib.net/docs](https://lrclib.net/docs)），**契约未核实** |
| Genius | 无公开 API；抓取违反 ToS | **不建议** |
| Musixmatch | 付费 | 不建议 |

> ⚠️ 这些契约我在本沙箱里**无法核实**——所有外部 host 都解析到非公网 IP，web_fetch 全部失败，
> 我只能通过搜索结果确认这些项目/文档**存在**。要用之前请自己核一遍端点和条款。

## 3. 乐评

### 3.1 Apple 自己的编辑评语（已实测，免费且合规）

`GET /v1/catalog/{sf}/songs/{id}?include=albums` → 专辑 `attributes` 里就有：

```
editorialNotes { short, standard }     ← Apple 的编辑评语
contentRating   recordLabel   upc   copyright
isCompilation   isSingle   isMasteredForItunes   trackCount
```

**授权内容、无需抓取、现有凭据即可。** 代价是每首歌一次 `include=albums`（或者按专辑去重后批量查）。

**覆盖问题是下一步该测的第一件事**：`editorialNotes` 主要出现在**被编辑推荐过**的发行上，
独立/同人发行常常没有。我没测——而这个数字直接决定方向 3 值不值得做。

### 3.2 外部源

| 源 | 内容 | 门槛 | 状态 |
|---|---|---|---|
| **Last.fm** | 专辑 wiki 摘要 + listener/playcount | 免费 key | 搜索确认存在（[API 文档](https://cs.wellesley.edu/~mashups/pages/APIs/lastfm_docu.pdf)），未核实 |
| **Discogs** | 社区评分 + 风格标签 + release notes | 免费 token | 搜索确认存在，未核实 |
| **网易云 / QQ 评论** | 中文乐评 / 歌曲评论 | **非官方，抓取** | 只有第三方 scraper（[例](https://apify.com/getascraper/netease-music-comments-scraper/input-schema#1)） |
| AllMusic / Pitchfork / Metacritic | 专业乐评 | 无干净 API，抓取违反 ToS | **不建议** |

**一条重要的语义区分**：**评论区热度是"流行度"，不是"质量"。**
网易云评论 999+ 说明它病毒式传播，不说明它好。把它当质量分会系统性偏向爆款——
最多只能当"文化可见度"，而且必须单独命名，不能叫 rate/score。

### 3.3 乐评的用法（重申第 1 节）

- **质量先验**：避免 deep cut 与 filler
- **语境**：`editorialNotes` 给 agent 素材，去解释"为什么这张专辑值得进这张歌单"——直接提升输出质量
- **`contentRating`**：用户要求干净版时用来过滤

**不要**把它们混进排序 cost。

## 4. 建议的落地顺序

| # | 做什么 | 为什么排这个位置 |
|---|---|---|
| 1 | **测 `editorialNotes` 覆盖率** | 最便宜、纯读、零风险。这个数字决定方向 3 的价值 |
| 2 | **`hasLyrics` 持久化 + 漏斗加 `no-lyrics`** | 持久化那一半**已经做了**（`am_library`）。让"能评价多少"可测量 |
| 3 | **歌词情感打分（本地词表）** | 同时解掉版权和"不内嵌 LLM"两个约束。**但要你先决定词表数据怎么办** |
| 4 | **跨曲呼应检测** | 纯离线，有了歌词特征就能做，最有"有意思"的回报 |
| 5 | **Last.fm / Discogs 质量先验** | 需要你去申请 key / token |
| 6 | 网易云评论 | **最后再说**：非官方接口 + 语义是流行度而非质量 |

## 5. 我没能验证的（诚实清单）

- **Last.fm / Discogs / LRCLIB / 网易云的具体契约** —— 本沙箱所有外部 host 都解析到非公网 IP，
  `web_fetch` 全部失败。搜索只能确认它们**存在**，不能确认端点与条款。
- **`editorialNotes` 的覆盖率** —— 没测。
- **情感词表的实际效果**，尤其中文和日文 —— 没测。这是整个方向 3 成败的关键，不该拍脑袋。
- **歌词端点会不会限流** —— 没测。网页 token 的配额是共享的，45 首的歌单就是 45 次请求。
- **LRCLIB 与 Apple 歌词的互补度** —— 即 Apple 没有的那 35% 里，LRCLIB 能补多少。这是决定要不要接
  第二个歌词源的关键数字，同样没测。

## 6. 一句话

**歌词值得接，乐评要接对地方。** 歌词的最大价值不是"给情绪打分"——项目已经有一个音频 valence 了——
而是**把主题契合从猜测变成有据**，以及让跨曲呼应这类"有意思"的东西第一次可以被自动发现。
乐评的最大价值是**质量先验和语境**，而它**必须停在选曲那一侧**。
